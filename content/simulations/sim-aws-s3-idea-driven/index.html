AWS S3

IDEA-BASED ENGINEERING · 30 VISUAL CARDS · FROM FIRST PRINCIPLES

Imagine that cloud storage does not exist yet. We have computers, hard disks and applications that continuously generate information.

Our objective is to build a storage system that can grow independently of computers, survive infrastructure failures, securely serve millions of users and automatically manage the information stored inside it.

Phase 01 — Discovering the storage problem

01 / 30 · THE ORIGINAL DESIGN

Storing files on a single computer

We build an application that saves photographs and documents directly onto its computer's hard disk. Reading and writing data is straightforward because everything exists in one place.

Initial architecture

Computing and persistent storage are tightly coupled.

What happens when the disk becomes full?

Our application becomes popular. Every new user uploads more photographs, but the physical disk has a fixed capacity.

Buying a larger disk temporarily solves the problem. But we will encounter the same limitation again.

New requirement

Storage capacity must grow without replacing the entire computer.

03 / 30 · SINGLE POINT OF FAILURE

What happens when the computer fails?

A failed computer makes its application and local files unavailable. If the disk itself is permanently damaged and no backup exists, the information may be lost.

Application unavailable
Potential permanent data loss
Idea discovered

The lifetime of valuable information should not depend on the lifetime of one machine.

04 / 30 · ARCHITECTURAL DECOUPLING

Separate storage from computing

Move persistent information into a separate storage service. Application servers communicate with that service instead of depending on their own local disks.

Compute
Scale processing independently.
Storage
Scale capacity independently.
Reusable engineering idea

Separate components that have different scaling requirements and failure characteristics.

05 / 30 · SERVICE ABSTRACTION

Make storage accessible over a network

Introduce a network-accessible service that accepts requests to store and retrieve information. Applications no longer need to know which physical disk holds their data.

This gives us the foundation for a managed storage service.

Reusable engineering idea

Hide infrastructure complexity behind a stable service interface.

Phase 02 — Inventing object storage

06 / 30 · RECONSIDERING THE FILE SYSTEM

Do we really need physical folders?

Traditional file systems organize information into directories. But our network storage service primarily needs to locate and return complete pieces of information.

Instead of requiring a conventional directory structure, give every stored item a unique key within a container. The key itself can include slashes to represent logical organization.

General purpose S3 buckets use this object-based model rather than conventional file-system semantics.

Idea discovered

Logical organization does not have to mirror physical storage organization.

07 / 30 · THE FUNDAMENTAL DATA STRUCTURE

Invent an object: data + identity + metadata

The information must carry an identity for retrieval and descriptive properties for management.

Key
Identifies the object within its bucket.
Data
The actual sequence of bytes.
Metadata
System-defined or user-defined properties.

This self-contained storage unit is called an object. When versioning is enabled, individual versions also have their own version IDs.

08 / 30 · NAMESPACE ISOLATION

Inventing buckets

Two applications want to store an object named report.pdf. How do we prevent their keys from conflicting?

Create named containers called buckets. An object's identity now includes both its bucket and its key.

OBJECT A
s3://finance-data/report.pdf
OBJECT B
s3://research-data/report.pdf

The two objects can coexist. Buckets also establish a boundary for configuration, access control and data management.

Reusable engineering idea

Introduce namespaces to isolate identifiers and administrative responsibilities.

09 / 30 · LOGICAL ORGANIZATION

Invent keys and prefixes

How can we organize millions of objects without requiring conventional nested directories?

Give related objects keys that begin with the same string. We can then list or manage objects by prefix.

FILTER BY PREFIX
photos/2026/January/
2 matching objects

The entire string remains the object key. In general purpose buckets, the folder-like display is a logical interpretation of prefixes.

10 / 30 · STANDARDIZED OPERATIONS

Build the object storage API using HTTP

We need a common language through which any application can manipulate objects, regardless of its operating system or programming language.

Define predictable operations that accept a bucket, an object key and other request parameters.

Example AWS CLI operations
aws s3 cp photo.jpg s3://my-bucket/photos/
aws s3 ls s3://my-bucket/photos/
aws s3 cp s3://my-bucket/photos/photo.jpg .
Requires an existing bucket, configured AWS credentials and appropriate permissions. Requests may incur charges.

We have now constructed the fundamental interface of Amazon Simple Storage Service (S3).

Reusable engineering idea

Standardize operations so clients can use a service without understanding its internal implementation.

Phase 03 — Engineering distributed storage

11 / 30 · HORIZONTAL SCALING

Distribute objects across storage machines

Our storage API works. But if every object ultimately goes into one disk, we still have the capacity problem from Card 02.

Instead of growing one disk indefinitely, introduce a pool of independent storage nodes. A placement mechanism determines where incoming information should reside.

Additional machines increase total capacity. The client-facing object key remains unchanged even if the underlying storage placement changes.

Reusable engineering idea

Horizontal scaling expands a resource pool instead of continually enlarging one machine.

12 / 30 · FAULT TOLERANCE

Protect information through redundancy

Distribution increases capacity, but losing a storage node could still destroy the objects assigned to it. We must introduce redundant information across independent failure domains.

Conceptual redundancy model, not a claim about S3's exact replica count or encoding implementation.

S3 Standard is designed to withstand the loss of an entire Availability Zone by storing data redundantly across multiple zones. Some other storage classes intentionally use just one zone.

Reusable engineering idea

Redundancy is most valuable when redundant resources do not share the same failure conditions.

13 / 30 · DATA INTEGRITY

Detect corrupted information using checksums

What if an object arrives successfully, but some of its bytes have changed during transmission?

Illustrative checksum values.

Calculate a compact fingerprint from the bytes before transmission. Recalculate it after receiving the information and compare the two results.

S3 supports checksum algorithms that validate uploaded information and can be used to verify downloads. An ETag should not be assumed to be a full-object MD5 checksum.

Reusable engineering idea

Verify data independently of whether its transport operation reports success.

14 / 30 · RELIABILITY METRICS

Durability is not the same as availability

Imagine that our storage service preserves every photograph perfectly but cannot respond to requests for ten minutes. Is the information lost? No. Is it accessible? Also no.

DESIGNED DURABILITY
99.999999999%
Will data survive?
Protection against permanent loss.
DESIGNED AVAILABILITY
99.99%
Can I access it?
Ability to serve requests.

These are the design targets for S3 Standard, not guarantees that every individual request succeeds. Different storage classes have different availability characteristics.

Reusable engineering idea

Measure information survival separately from service responsiveness.

15 / 30 · CONSISTENCY

What should happen immediately after a write?

An application replaces report.pdf with a newer version. Another application immediately requests the same key. Should it receive the old report or the new one?

S3 provides strong read-after-write consistency for object creation, replacement and deletion, including subsequent listing operations. This does not turn multiple independent object updates into a single atomic transaction.

Reusable engineering idea

Clearly define when a completed operation becomes observable to other clients.

16 / 30 · DIVIDE AND CONQUER

Upload enormous objects in smaller parts

A 1 GB upload fails just before completion. Restarting the entire transfer wastes all the successfully transmitted information.

UPLOAD SESSION
CreateMultipartUpload
Initialize
UploadPart
Transfer in parallel
CompleteMultipartUpload
Assemble

Upload smaller parts independently, retry failed parts and finalize the object after all parts succeed. Unfinished multipart uploads should be completed or aborted to avoid ongoing storage charges.

Reusable engineering idea

Break expensive operations into independently recoverable units.

Phase 04 — Securing distributed storage

17 / 30 · SECURE DEFAULTS

Make stored objects private by default

Our storage service is accessible through a network. But accessible does not mean everybody should be able to read its contents.

Block Public Access
Enabled by default on new buckets.
ON
Object Ownership
Bucket owner enforced by default; ACLs disabled.

Require an explicit authorization decision rather than allowing unknown users to access data.

Reusable engineering idea

Design systems that remain protected even when no additional security configuration has been supplied.

18 / 30 · IDENTITY-BASED AUTHORIZATION

Different identities need different permissions

A processing service needs to read photographs. An upload service needs to create photographs. Neither necessarily needs permission to delete everything.

Attach permission policies to IAM users or roles. Applications should generally use roles with temporary credentials rather than embedded long-lived access keys.

Reusable engineering idea

Least privilege: provide each identity with only the capabilities required to perform its responsibility.

19 / 30 · RESOURCE-BASED AUTHORIZATION

Give the bucket its own access rules

Identity policies describe what a requester can do. But the owner of a resource should also be able to specify who can access it.

Introduce resource-based policies that identify a principal, a permitted action and the resources covered by that permission.

EXAMPLE BUCKET POLICY · READ-ONLY ACCESS TO REPORTS
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::123456789012:role/ReportReader"
    },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-bucket/reports/*"
  }]
}
PrincipalReportReader role
ActionRead objects
Resourcereports/* prefix

The final authorization decision depends on the applicable AWS policies and restrictions. An applicable explicit deny overrides an allow.

Reusable engineering idea

Separate security rules from application code and place authorization controls at resource boundaries.

A presigned URL grants a limited operation using the signer's authorization. Anyone holding a usable URL can generally exercise that permission until it expires or becomes invalid, so treat it as sensitive. It is not inherently single-use.

Reusable engineering idea

Delegate narrowly scoped capabilities that expire instead of distributing permanent credentials.

21 / 30 · CONFIDENTIALITY

Protect data during transmission and storage

Authorization decides who may request data. Encryption addresses a different problem: preventing unauthorized parties from understanding protected data.

TLS
Protects the network connection.
SSE-S3
Server-side encryption with S3-managed keys.
SSE-KMS
Encryption using AWS KMS key management.

S3 encrypts new uploads at rest by default with SSE-S3 unless another supported encryption configuration is selected. HTTPS protects communication in transit. Encryption does not replace authorization.

Reusable engineering idea

Protect information independently at each boundary through which it passes.

Phase 05 — Optimizing storage economics

22 / 30 · UNDERSTANDING ACCESS PATTERNS

Not all information has equal access frequency

Today's photographs may be viewed hundreds of times. Last year's photographs may be viewed occasionally. A five-year-old backup might never be opened unless a disaster occurs.

Illustrative access pattern; real workloads may behave differently.
Hot data
Product photographs and active documents.
Warm data
Previous monthly reports.
Cold data
Long-term archives and historical backups.

Maintaining every object on the same expensive storage tier is unnecessary when workloads have substantially different access requirements.

Idea discovered

Allocate storage resources according to the expected future usage of information.

24 / 30 · POLICY-DRIVEN AUTOMATION

Let objects manage their own storage lifecycle

We can manually move older objects to cheaper storage. But what happens when we manage billions of objects?

Example lifecycle for eligible, sufficiently large, noncurrent-version-independent log objects in an unversioned bucket.

Create declarative rules describing when an object should move to another storage class or expire.

EXAMPLE · S3 LIFECYCLE CONFIGURATION
{
  "Rules": [{
    "ID": "LogLifecycle",
    "Status": "Enabled",
    "Filter": {"Prefix": "logs/"},
    "Transitions": [
      {"Days": 30, "StorageClass": "STANDARD_IA"},
      {"Days": 90, "StorageClass": "GLACIER"}
    ],
    "Expiration": {"Days": 365}
  }]
}

S3 evaluates lifecycle eligibility and performs the configured actions asynchronously. Versioned buckets require additional consideration for noncurrent versions and delete markers. Expiration can permanently remove information, so retention rules must be selected carefully.

Reusable engineering idea

Express resource-management intentions as policies rather than repeatedly executing manual operations.

25 / 30 · PRESERVING HISTORICAL STATE

What if somebody overwrites or deletes important data?

Redundancy protects against infrastructure failures, but redundant storage alone does not prevent the system from faithfully executing an accidental deletion.

Instead of destroying the existing information whenever its key is overwritten, retain the previous object version.

Object version history
Delete marker
Current
Version C
Retained
Version B
Retained
Version A
Retained

With S3 Versioning enabled, a normal delete request creates a delete marker. Earlier versions remain retrievable unless permanently deleted or expired. Restoring a previous version can be done without discarding every subsequent version. Retained versions consume storage.

Reusable engineering idea

Represent change as a sequence of preserved states rather than destructive replacement.

26 / 30 · IMMUTABILITY

Prevent even authorized users from deleting protected information

Versioning helps us recover information, but someone with permanent-delete permission might still remove its historical versions.

Introduce a retention mechanism that makes specific object versions immutable for a specified period.

Governance mode
Privileged users with bypass permission may override retention.
Compliance mode
Protected versions cannot be deleted before retention expires, even by the account root user.
Legal hold
Protection remains until an authorized user removes the hold.

S3 Object Lock requires versioning and implements the write-once, read-many (WORM) storage model. It protects specific versions, not the key from acquiring new versions or delete markers.

Reusable engineering idea

Enforce immutability at the storage layer when preservation is more important than modification flexibility.

Phase 06 — Building an intelligent storage ecosystem

27 / 30 · GEOGRAPHICAL REDUNDANCY

What if an entire geographical region becomes unavailable?

We have protected information against individual infrastructure failures. But a critical business might require an independently maintained copy of its information in another geographical region.

Create a replication policy that copies eligible object versions to another bucket.

Cross-Region Replication (CRR)
Replicate across different AWS Regions.
Same-Region Replication (SRR)
Replicate between buckets in the same Region.

Live S3 replication is asynchronous, requires versioning on the source and destination buckets, and normally applies to eligible new objects or updates. Existing objects can be replicated using S3 Batch Replication. Replication is not automatic application failover.

Reusable engineering idea

Expand redundancy across increasingly independent failure domains according to business recovery requirements.

28 / 30 · EVENT-DRIVEN ARCHITECTURE

What if storage could trigger computation?

Every time someone uploads a photograph, we want to generate a thumbnail, inspect the file and update a database.

Should our application continuously check the bucket for new objects?

Rather than repeatedly searching for changes, configure the storage service to generate a notification when a relevant operation occurs.

Simplified object-created event
{
  "eventName": "ObjectCreated:Put",
  "s3": {
    "bucket": {"name": "my-bucket"},
    "object": {"key": "uploads/mountain.jpg"}
  }
}
Illustrative excerpt from an S3 notification record.

Events can be routed to AWS Lambda, SQS, SNS or EventBridge. Consumers must account for duplicate notifications and possible out-of-order delivery. Use separate output prefixes or buckets to avoid recursive processing loops.

Reusable engineering idea

Replace continuous polling with event-driven communication. Producers announce changes; independent consumers respond.

29 / 30 · STORAGE AS A DATA PLATFORM

Build a data lake using object storage

A company receives millions of records from applications, sensors, transactions and logs. Instead of building a separate storage infrastructure for every data source, create one shared foundation.

Illustrative data lake organization
EXAMPLE · ANALYTICS QUERY
SELECT event_type, COUNT(*) AS total
FROM application_events
GROUP BY event_type;

Athena can query data stored in S3 once the required table and schema are configured. Other processing services can transform the data or use it for machine learning. The storage service itself is not executing the SQL query.

Reusable engineering idea

Store information independently of the processing engine so multiple systems can derive value from the same data.
