Linux Kernel — Recreating the invention

Idea-Driven Learning · 60 cards · 10 phases

Imagine a computer with no operating system. We will design a resource manager from scratch, one problem at a time. Each card tests an idea and exposes a new engineering decision. This is a logical reconstruction, not a literal history or exhaustive kernel implementation.

Phase 1 — Why do we need a kernel?

IDEA 01 / 60

How can we make hardware execute instructions?

The CPU cannot understand a user's intention. It can execute encoded instructions.

Develop the idea — thought experiment

Put 3 and 4 in registers, issue ADD, then store 7 in RAM. Change ADD to SUB: the hardware now produces −1.

Invention: Instruction set and stored-program computation.

Reusable idea: Represent behavior as executable data.

IDEA 02 / 60

How does the first program start?

After reset, RAM does not contain a ready application.

Develop the idea — thought experiment

Give the CPU a predefined reset address. Firmware initializes enough hardware to load a bootloader, which loads our kernel and hands over control.

Invention: Bootstrapping.

Reusable idea: Use a small trusted initializer to start a larger system.

IDEA 03 / 60

How can we load another program?

Our boot code can execute but an application on disk is only bytes.

Develop the idea — thought experiment

Place the executable's code and data in memory, prepare a stack, then set the instruction pointer to its entry address. A real ELF loader also handles mappings and permissions.

Invention: Executable loading.

Reusable idea: Separate a stored artifact from its running instance.

IDEA 04 / 60

What if programs compete for hardware?

Two applications want the same disk and memory. Neither knows what the other is doing.

Develop the idea — thought experiment

Let A write a block, then B overwrite the same block. A's data disappears. Introduce one authority to allocate blocks and coordinate access.

Invention: Resource ownership.

Reusable idea: Centralize arbitration of shared resources.

IDEA 05 / 60

What if a manager stays in control?

A temporary loader cannot coordinate programs after handing them control.

Develop the idea — thought experiment

Keep a privileged manager resident in memory; ask it to allocate resources, run tasks and operate devices instead of letting each application manage everything.

Invention: Resident kernel.

Reusable idea: Separate shared infrastructure from applications.

IDEA 06 / 60

How do we stop programs from taking over?

If every program can disable interrupts or modify any memory, a bug can destroy the system.

Develop the idea — thought experiment

Run applications in a restricted CPU privilege level. A privileged instruction from an app traps; the kernel decides what to do.

Invention: User mode and kernel mode.

Reusable idea: Enforce trust boundaries in hardware or a protected runtime.

Phase 2 — Inventing processes

IDEA 07 / 60

How can a running program have an identity?

Starting the same executable twice gives us two independent activities.

Develop the idea — thought experiment

Assign each instance a process ID, its own execution context and resources. Two copies of editor now have different PIDs and state.

Invention: Process abstraction.

Reusable idea: Give independent work a stable identity and lifecycle.

IDEA 08 / 60

How do we preserve a program's progress?

A process is more than its executable bytes. It may be halfway through a calculation.

Develop the idea — thought experiment

Pause when PC=120 and R1=7. Save the PC, stack pointer and registers, then restore them before resuming. Keep other task metadata in a kernel record.

Invention: Task context and task_struct.

Reusable idea: Persist enough state to resume work accurately.

IDEA 09 / 60

How can a program create another program?

Our shell wants to launch a new activity without disappearing.

Develop the idea — thought experiment

Imagine a parent at PID 101 asking for a child. Give the child PID 102 and initially share suitable resources; fork uses copy-on-write for ordinary private memory.

Invention: Process creation (fork/clone).

Reusable idea: Create independent work from a parent context.

IDEA 10 / 60

How can a process become a different program?

A child shell should run a compiler, not keep executing the shell code.

Develop the idea — thought experiment

Replace the child's address space with a new executable using execve; keep its PID and selected inherited resources. The old program does not resume on success.

Invention: Exec and program replacement.

Reusable idea: Separate identity from the implementation currently running.

IDEA 11 / 60

How do we track thousands of processes?

A list of anonymous activities cannot answer who is running or waiting.

Develop the idea — thought experiment

Maintain records indexed by identity, with state and relationships. Look up PID 102 and discover that it is waiting for I/O; Linux exposes a view via procfs.

Invention: Task bookkeeping and process state.

Reusable idea: Model a system as inspectable state machines.

IDEA 12 / 60

How do we terminate a process?

A program has finished but still owns memory and open files.

Develop the idea — thought experiment

Mark it exited, release resources no longer referenced, and preserve exit status until a parent collects it with wait. An unreaped child can briefly remain a zombie.

Invention: Exit, wait and resource lifetime.

Reusable idea: Distinguish completion from final cleanup.

Phase 3 — Inventing CPU scheduling

IDEA 13 / 60

How can one CPU serve many programs?

If a compiler runs until completion, the editor cannot respond.

Develop the idea — thought experiment

Alternate between the compiler and editor. Neither completes instantly, but both make progress on the same CPU.

Invention: Time multiplexing.

Reusable idea: Share a scarce resource across independent clients.

IDEA 14 / 60

What if we divide CPU time into intervals?

A cooperative task may never volunteer to stop.

Develop the idea — thought experiment

Use a timer interrupt to let the kernel regain control. In a toy round-robin model, six 2 ms slots give two equal tasks 6 ms each. Real Linux scheduling is more nuanced.

Invention: Preemptive multitasking.

Reusable idea: Bound how long any one client monopolizes a resource.

IDEA 15 / 60

How can we pause and resume execution?

Switching to a different task destroys the current register contents unless we preserve them.

Develop the idea — thought experiment

Save A's execution context, choose B, load B's context, and switch address-space context when needed. Later reverse the operation.

Invention: Context switching.

Reusable idea: Separate work state from the worker executing it.

IDEA 16 / 60

How do we prioritize important tasks?

An interactive app needs quick responses while a batch task can wait.

Develop the idea — thought experiment

Compare equal time shares with weighted service: give the interactive job more timely opportunities while preserving progress for others. Linux fair scheduling and real-time classes differ.

Invention: Scheduling policy and priorities.

Reusable idea: Trade off fairness, latency and throughput explicitly.

IDEA 17 / 60

How can sleeping processes avoid wasting CPU time?

A process waiting for a disk read has no useful instructions to execute.

Develop the idea — thought experiment

Remove it from runnable work, keep it on a wait queue, and wake it when I/O completes. Other ready tasks use the CPU meanwhile.

Invention: Blocking, wait queues and wakeups.

Reusable idea: Schedule only work that can make progress.

IDEA 18 / 60

How do we distribute work across CPU cores?

One core is overloaded while another is idle.

Develop the idea — thought experiment

Give each core a runnable queue; move eligible work to an idle core if balancing benefits outweigh migration costs. Keep cache affinity in mind.

Invention: SMP scheduling and load balancing.

Reusable idea: Balance demand against locality.

Phase 4 — Inventing memory management

IDEA 19 / 60

How can multiple programs share RAM?

A program that writes physical address 100 may overwrite another's data.

Develop the idea — thought experiment

Give A and B nonoverlapping physical regions and enforce their bounds. Fixed regions help isolation but constrain growth and placement.

Invention: Memory allocation and protection.

Reusable idea: Partition a finite resource and enforce ownership.

IDEA 20 / 60

What if every program sees private addresses?

Requiring each program to know where it physically lives makes loading and isolation difficult.

Develop the idea — thought experiment

Let A and B both access virtual address 0x1000. Map A to one physical frame and B to another.

Invention: Virtual address spaces.

Reusable idea: Separate logical identity from physical placement.

IDEA 21 / 60

How can imaginary addresses reach real memory?

The CPU needs to find actual bytes from virtual addresses on every access.

Develop the idea — thought experiment

Split a virtual address into page number and offset. Consult page tables using the MMU; combine the mapped frame with the unchanged offset. Cache translations in the TLB.

Invention: Address translation, page tables and TLB.

Reusable idea: Use indirection plus caching to hide physical layout.

IDEA 22 / 60

Why divide memory into fixed-size pages?

Variable-size allocations make finding contiguous free physical space difficult.

Develop the idea — thought experiment

Divide RAM into equal frames. Map three consecutive virtual pages to frames 2, 7 and 4. They need not be physically adjacent.

Invention: Paging.

Reusable idea: Use fixed-size chunks to simplify placement and reuse.

IDEA 23 / 60

What if we allocate memory only when needed?

A program reserves a huge address range but touches only a tiny part.

Develop the idea — thought experiment

Reserve four virtual pages; initially leave them unbacked. On a valid first access, handle the page fault and provide a backing page. Invalid access remains an error.

Invention: Demand paging and page faults.

Reusable idea: Defer allocation until actual use.

IDEA 24 / 60

How can programs share data without copying everything?

Forking a process with 100 private pages would be expensive if all pages were copied immediately.

Develop the idea — thought experiment

Initially share read-only mappings. When the child writes one page, copy that page and update its mapping. The parent retains the old content.

Invention: Copy-on-write.

Reusable idea: Share immutable state; copy only when mutation requires it.

IDEA 25 / 60

What if physical RAM becomes insufficient?

All frames are occupied and a new allocation arrives.

Develop the idea — thought experiment

Reclaim clean file-backed pages first where suitable; dirty data may need writeback and anonymous pages may need swap. If reclaim fails, the kernel may invoke OOM handling.

Invention: Memory reclaim, swap and OOM.

Reusable idea: Handle overload with reclaim and explicit failure policy.

IDEA 26 / 60

How can the kernel allocate efficiently?

A kernel needs both large groups of pages and many tiny objects.

Develop the idea — thought experiment

Use a buddy allocator to split blocks of pages; build slab caches for repeatedly allocated objects. Reuse a freed object rather than acquiring a whole new page each time.

Invention: Buddy and slab allocation.

Reusable idea: Use hierarchical allocation and object pools.

Phase 5 — Inventing filesystems

IDEA 27 / 60

How can information survive power loss?

RAM loses ordinary data when power is removed.

Develop the idea — thought experiment

Write numbered blocks to persistent storage, then read block 12 after reboot. The device preserves bytes, but we still need a way to find meaningful objects.

Invention: Persistent block storage.

Reusable idea: Separate durable state from volatile execution.

IDEA 28 / 60

How do we turn raw blocks into named files?

A user wants notes.txt, not block numbers.

Develop the idea — thought experiment

Store metadata mapping a name to a file record, and that record to blocks or extents. A directory organizes names.

Invention: Files and directories.

Reusable idea: Provide meaningful names over low-level storage.

IDEA 29 / 60

How can a file have multiple names?

Renaming a file should not copy all its contents.

Develop the idea — thought experiment

Give the file an inode identity. Directory entries notes.txt and draft.txt can refer to the same inode through hard links. Removing one name need not remove the data.

Invention: Inodes and directory entries.

Reusable idea: Separate identity from aliases.

IDEA 30 / 60

How can a program remember an open file?

Resolving a pathname on every read is inefficient and the name may change.

Develop the idea — thought experiment

Return a small file descriptor from open. The descriptor points to an open file description that holds offset and flags; two independent opens may have different offsets.

Invention: File descriptors.

Reusable idea: Use handles for ongoing resource access.

IDEA 31 / 60

How can different filesystems use the same interface?

An application should not need separate read logic for ext4 and tmpfs.

Develop the idea — thought experiment

Provide common operations such as open and read. Dispatch each operation through the virtual filesystem to the filesystem-specific implementation.

Invention: Virtual filesystem (VFS).

Reusable idea: Define a stable interface with replaceable implementations.

IDEA 32 / 60

Why read data that is already in RAM?

Repeatedly reading a file from disk wastes time.

Develop the idea — thought experiment

Keep its pages in the page cache. First access fetches storage; later access can use cached memory. Dirty cached data needs writeback and durability controls.

Invention: Page cache.

Reusable idea: Cache expensive resources near consumers.

IDEA 33 / 60

How can storage recover after a crash?

A crash between updating file metadata and allocation can leave inconsistent state.

Develop the idea — thought experiment

Record a metadata transaction in a journal, commit it, then update its home locations. Replay committed transactions after a crash. Data durability still depends on filesystem mode and sync operations.

Invention: Journaling and crash consistency.

Reusable idea: Make multi-step changes recoverable.

Phase 6 — Inventing hardware communication

IDEA 34 / 60

How can software communicate with hardware?

A CPU instruction does not automatically know how a disk controller works.

Develop the idea — thought experiment

Expose device registers or I/O ports. Write a request through the device's defined interface, then examine status. The exact protocol depends on hardware.

Invention: Device I/O and MMIO.

Reusable idea: Treat a device as a controlled protocol endpoint.

IDEA 35 / 60

What if each device had a translator?

Every application should not implement every printer and disk protocol.

Develop the idea — thought experiment

Move device-specific control into a driver. Applications use stable kernel interfaces while drivers handle the actual hardware.

Invention: Device drivers.

Reusable idea: Hide implementation differences behind adapters.

IDEA 36 / 60

Can hardware tell us when it is ready?

Polling a device in a loop consumes CPU time.

Develop the idea — thought experiment

Start a request and run other work. When the device raises an interrupt, the kernel handles the event and schedules any necessary follow-up.

Invention: Interrupts.

Reusable idea: Replace constant polling with event notification.

IDEA 37 / 60

Can a device move data without the CPU copying every byte?

Copying a large packet byte by byte occupies the processor.

Develop the idea — thought experiment

Configure a DMA transfer between a device and a mapped RAM buffer. Let the device transfer data and notify the CPU at completion. DMA mapping and synchronization remain important.

Invention: Direct memory access (DMA).

Reusable idea: Offload repetitive movement to specialized engines.

IDEA 38 / 60

How can slow hardware avoid blocking all applications?

Disk operations can take far longer than a CPU instruction.

Develop the idea — thought experiment

Queue a read, let the caller sleep or continue via asynchronous I/O, and run other tasks until completion. Use a completion event to deliver the result.

Invention: Asynchronous and queued I/O.

Reusable idea: Decouple submission from completion.

IDEA 39 / 60

How can we extend a kernel without rebuilding it?

Not every driver is needed on every computer.

Develop the idea — thought experiment

Load a compatible kernel module that registers new driver functionality. Unload only when safe and unused; module loading requires privilege and may require signatures.

Invention: Loadable kernel modules.

Reusable idea: Extend a running core through controlled plugins.

Phase 7 — Inventing communication and synchronization

IDEA 40 / 60

How can isolated processes exchange information?

Isolation prevents A from casually reading B's memory, but they must cooperate.

Develop the idea — thought experiment

Create an explicit kernel-managed channel or a shared memory region with agreed access. Send data only through the authorized mechanism.

Invention: Interprocess communication (IPC).

Reusable idea: Create explicit channels across isolation boundaries.

IDEA 41 / 60

What if output becomes another program's input?

A text producer and a filter should cooperate without intermediate files.

Develop the idea — thought experiment

Connect A's output to B's input using a pipe. A writes bytes into a bounded kernel buffer; B consumes them. Full buffers apply backpressure.

Invention: Pipes.

Reusable idea: Compose small independent workers with streams.

IDEA 42 / 60

How can a process receive a notification?

A process may need to know that another process or the kernel detected an event.

Develop the idea — thought experiment

Send a permitted signal such as SIGTERM. The recipient can handle or ignore certain signals; SIGKILL cannot be caught or ignored.

Invention: Signals.

Reusable idea: Separate event notification from data transport.

IDEA 43 / 60

What if workers modify the same value simultaneously?

Two tasks increment a shared counter initially equal to 0.

Develop the idea — thought experiment

Both read 0, both compute 1, and both store 1. The expected final count was 2. The lost update shows why interleaving matters.

Invention: Race conditions.

Reusable idea: Protect invariants, not just individual instructions.

IDEA 44 / 60

How do we coordinate access to shared resources?

A shared counter update requires a read-modify-write sequence.

Develop the idea — thought experiment

Protect the critical section with a mutex: A increments to 1, releases; B increments to 2. Atomic operations are another option for simple counters; context determines lock choice.

Invention: Synchronization and locks.

Reusable idea: Make compound state transitions safe.

IDEA 45 / 60

What if tasks wait for each other forever?

A holds lock X and needs Y, while B holds Y and needs X.

Develop the idea — thought experiment

Draw the circular dependency. Prevent it by requiring both tasks to acquire X before Y, or redesign the interaction.

Invention: Deadlock prevention.

Reusable idea: Impose consistent ordering on shared resources.

Phase 8 — Inventing networking

IDEA 46 / 60

How can two computers exchange information?

A CPU cannot directly access a distant computer's memory.

Develop the idea — thought experiment

Encode data into a frame, send through a network interface, and receive it at another machine. Layers add addressing and protocol rules.

Invention: Network interfaces and protocol layers.

Reusable idea: Define messages across machines instead of sharing memory.

IDEA 47 / 60

Why divide a large message into packets?

A large continuous stream is hard to route and share with other traffic.

Develop the idea — thought experiment

Split a message into smaller protocol units, each with addressing or sequencing information as appropriate. Reassemble or consume at the receiving protocol layer.

Invention: Packet switching.

Reusable idea: Divide communication into independently manageable units.

IDEA 48 / 60

How does incoming data reach the correct app?

A host receives traffic for many applications at once.

Develop the idea — thought experiment

Inspect protocol and addressing information; match the packet to the appropriate socket using local and remote addresses and ports where applicable.

Invention: Sockets and demultiplexing.

Reusable idea: Route events to the correct consumer using identifiers.

IDEA 49 / 60

How do we communicate reliably over an unreliable network?

A packet may be lost, delayed or arrive out of order.

Develop the idea — thought experiment

Send numbered bytes, acknowledge received data, retransmit missing data, and control sending rate. TCP provides an ordered reliable byte stream, not guaranteed application success.

Invention: Reliable transport (TCP).

Reusable idea: Recover from partial failure with acknowledgement and retry.

IDEA 50 / 60

How can the kernel control network traffic?

Some packets should not enter or leave the system.

Develop the idea — thought experiment

Apply ordered filtering rules at network-stack hooks. Permit established traffic or drop a disallowed packet; Linux provides Netfilter and nftables infrastructure.

Invention: Packet filtering and firewall policy.

Reusable idea: Apply policy at a shared mediation point.

Phase 9 — Inventing security and isolation

IDEA 51 / 60

How can different users have different privileges?

Everyone can currently access every file and process.

Develop the idea — thought experiment

Attach user and group credentials to tasks and permission metadata to resources. Check credentials during access; deny a write when the policy does not permit it.

Invention: Credentials and access control.

Reusable idea: Associate actions with an identity and policy.

IDEA 52 / 60

How can an app safely request privileged operations?

A restricted application cannot directly access the disk but needs to read a file.

Develop the idea — thought experiment

Invoke a system call to enter the kernel. Validate pointers, arguments and permissions, perform the requested operation, then return a result or error.

Invention: System call boundary.

Reusable idea: Expose privileged services through narrow validated interfaces.

IDEA 53 / 60

How can privileges be limited instead of all or nothing?

Giving a network utility full administrative authority is excessive.

Develop the idea — thought experiment

Divide traditional root powers into capabilities. Give a task only the capability required for a particular authorized operation; consider its namespace and other security policy too.

Invention: Linux capabilities and least privilege.

Reusable idea: Grant narrowly scoped authority.

IDEA 54 / 60

What if each app saw a separate environment?

Two workloads should each see their own process tree and networking without changing every application.

Develop the idea — thought experiment

Give each group separate views of selected kernel resources: PID, mount, network and other namespaces. A PID may have different numbers in nested PID namespaces.

Invention: Namespaces.

Reusable idea: Provide separate logical views over shared infrastructure.

IDEA 55 / 60

How can we limit a group's resource consumption?

An isolated workload can still consume all RAM or CPU time.

Develop the idea — thought experiment

Place tasks into a cgroup hierarchy. Apply resource controls such as memory.max or cpu.max and account for consumption. A limit changes allocation policy, not the namespace view.

Invention: Control groups (cgroups).

Reusable idea: Measure and constrain resource usage by tenant.

IDEA 56 / 60

Can we build isolated environments using one kernel?

Separate namespaces alone do not define a complete isolated execution environment.

Develop the idea — thought experiment

Combine namespaces, cgroups, a filesystem view, restricted capabilities and other security controls. Both environments share the host kernel; isolation is not identical to a VM.

Invention: Containers.

Reusable idea: Compose orthogonal isolation mechanisms into a platform.

Phase 10 — Extending the invention

IDEA 57 / 60

How can we run multiple operating systems on one machine?

Containers share a kernel, but a workload needs a different guest kernel.

Develop the idea — thought experiment

Expose virtual CPUs, memory and devices to guests. KVM uses hardware virtualization support with userspace components such as QEMU to run virtual machines.

Invention: Hardware-assisted virtualization (KVM).

Reusable idea: Virtualize the entire resource interface, not just individual objects.

IDEA 58 / 60

Can we safely run custom logic inside the kernel?

Collecting every event in userspace may be expensive, but arbitrary kernel code is dangerous.

Develop the idea — thought experiment

Attach a small eBPF program to an allowed hook. A verifier checks safety properties before execution; helpers and attachment permissions constrain what it can do.

Invention: eBPF and verified extensibility.

Reusable idea: Run constrained code near data and events.

IDEA 59 / 60

How can we see what the kernel is doing?

A system is slow, but application logs cannot reveal where time is spent.

Develop the idea — thought experiment

Record scheduling, I/O or system-call events through tracing facilities such as tracepoints, ftrace or perf. Compare timestamps to locate the delay; observation has some overhead.

Invention: Kernel tracing and observability.

Reusable idea: Instrument boundaries to explain system behavior.

IDEA 60 / 60

What can we invent beyond Linux?

We now have many reusable design decisions, not merely a catalog of kernel features.

Develop the idea — thought experiment

Design a shared inference server: schedule requests, isolate tenants, cache models, meter memory, mediate privileges and trace latency. Compare its components to the kernel we reinvented.

Invention: Resource orchestration as a general engineering pattern.

Reusable idea: Build any shared platform from scheduling, isolation, abstraction and coordination.

What we actually invented

Linux kernel: a protected resource manager

Our design mediates access to shared hardware, provides reusable interfaces, manages competing activities and preserves isolation. Linux implements these ideas at production scale with many additional mechanisms.
